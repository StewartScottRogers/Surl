# Glossary

One term, one meaning, one name in code. When code or a document uses one of these
terms, it means exactly what is written here; when a concept below needs naming in code,
it uses the name in the "Name in code" column. "Not yet" means Phase 1 or later names it.

## Two programs named curl

| Term | Meaning | Name in code |
| --- | --- | --- |
| upstream curl | The original C implementation of curl, https://github.com/curl/curl. Surl's only oracle (ADR-0003). Always "upstream curl" when the distinction matters. | — |
| the Curl port | Stewart's C# port of curl, https://github.com/StewartScottRogers/Curl. Measured against Surl in the last phase; never used to validate Surl (ADR-0003). Always "the Curl port", never bare "Curl" when it could be misread. | — |
| pinned upstream build | An upstream curl executable identified by its SHA-256 in `UpstreamCurlBuilds.json`. The only kind of curl Surl's tools run. | `UpstreamCurlBuilds.json`, `Assert-PinnedUpstreamCurl` |
| reference release | The upstream curl release Surl is measured against: 8.21.0, released 2026-06-24, the release the Curl port targets. | — |

## Serving

| Term | Meaning | Name in code |
| --- | --- | --- |
| mate | The server that answers a given curl request. Surl is curl's mate. | — |
| listen URL | A URL given to `surl`: its scheme picks the protocol server, its host and port the bind address. | `ListenUrl` (ADR-0004) |
| protocol server | The library that answers one protocol family, secure variants included: `Surl.Protocol.<Name>.UnitLibrary`. | `IProtocolServer`, implemented through `IConnectionProtocolServer` or `IDatagramProtocolServer` (ADR-0004) |
| horizontal library | A library a protocol server may reference besides Abstractions, listed in ADR-0002's table. | `HorizontalLibraries` in `ProtocolIsolationTests` |
| data directory | The directory `--directory` names: its files are what every file-serving protocol server serves, and its `.surl` folder holds every other kind of service state, both surviving restarts. Without `--directory` there is none: surl serves an empty in-memory file system and keeps service state in memory (ADR-0031 decision 1, superseding ADR-0007's default of the current directory). Formerly "served directory". | `SurlCommandLine.DataDirectory` (`null` without `--directory`) |
| served root | The full path the content store is rooted at: the data directory's full path with `--directory`, `InMemoryContentFileSystem.RootPath` without it (ADR-0031 decision 1, ADR-0018). | `ContentStore.ServedRoot` |
| in-memory file system | The file system the content store serves without `--directory`: empty at start, lasting for the process lifetime, bounded by `InMemoryContentFileSystem.DefaultMaxTotalBytes` (256 MiB) and never touching the disk. Past the bound a write fails as on a full disk (ADR-0031 decision 4). The second `IContentFileSystem` implementation beside `DiskContentFileSystem`. | `InMemoryContentFileSystem` |
| service-state folder | `<data directory>/.surl`: where services keep state other than served files (`.surl/mqtt/retained-messages` for MQTT retained messages) and where the data-directory lock lives. Never served, listed or uploaded to, whatever `--serve-dot-files` and `--follow-symlinks` say; the match is the first path segment, case-insensitive (ADR-0031 decisions 5 and 6). | `DataDirectoryLock.StateFolderName` in `Surl.Console`; hidden by `ContentStore` |
| data-directory lock | `<data directory>/.surl/lock`, held open exclusively for as long as surl serves, so one surl process uses a path at a time. A second process given the same path gets `DataDirectoryInUse` (124); a `.surl` or lock file that cannot be created gets `CouldNotWriteFile` (23). The operating system releases it when the holder exits; the file is never deleted (ADR-0031 decision 7). | `DataDirectoryLock.Take`, returning a `DataDirectoryLockOutcome` |
| listener status line | The line `Listening on <scheme>://<host>:<bound port>/` surl writes to stdout for each listen URL once every listener has bound, from the `info` log level up, so `-s` and `-s -S` write none (ADR-0007, ADR-0033 section 1). | `ListenerStatusLine` in `Surl.Output.UnitLibrary` |
| verbose exchange log | What the `verbose` log level (`-v`) writes to the log stream: one line per exchange event, `#<exchange id> <marker> <text>`, the marker `<` for bytes received, `>` for bytes sent, `*` for a note (ADR-0007 section 8, ADR-0033 section 1). | `IExchangeLog`, `IExchangeLogFactory` (ADR-0004); `LevelledExchangeLogFactory` at `LogLevel.Verbose`, whose logs are `VerboseExchangeLog`, in `Surl.Output.UnitLibrary` |
| parsed command line | What `Surl.Cli` returns for a command line that serves: the listen URLs and every option value, defaults applied (ADR-0007). | `SurlCommandLine` |
| negatable option | A flag that `--no-<name>` turns off, as curl's boolean options are; the later of the two wins (ADR-0007). | `CommandLineOption.Negatable` in `Surl.Cli.UnitLibrary` |
| content store | The file tree under the served root that every file-serving protocol server publishes, read and written through an `IContentFileSystem`, and the rules that map request paths onto it without escaping it. | `ContentStore` in `Surl.Content.UnitLibrary` |
| exchange | One conversation between upstream curl and Surl, over one connection or one datagram flow, from accept to close. One `ServeAsync` call. | `ExchangeContext` (ADR-0004) |
| hardening limit | A bound on what a peer can make Surl hold - connections, time, bytes - with a default number, an option to change it, and 0 meaning no limit (ADR-0006). | `ExchangeLimits` for the per-exchange ones, `ConnectionLimits` in `Surl.Core.UnitLibrary` for the connection-level ones |
| idle timeout | How long an exchange may go with no byte moving in either direction on any of its transports before Surl closes it. 120 s by default (ADR-0006). | `ConnectionLimits.IdleTimeout` in `Surl.Core.UnitLibrary` |
| head timeout | How long a peer has to deliver a complete request head, command line or first packet; the slow-sender defence. 30 s by default (ADR-0006). | `ExchangeLimits.HeadTimeout` |
| connection refusal | The protocol's own "too busy" answer written to a connection or datagram flow accepted past a connection limit, before it is closed (ADR-0006). | `IConnectionRefusalWriter`, `IDatagramRefusalWriter`, `ConnectionRefusal` |
| exposure default | What a server offers until an option says otherwise: uploads, directory listings, symbolic links, dot-files. All off by default (ADR-0006). | `ContentExposureOptions` in `Surl.Content.UnitLibrary` |
| answered as absent | Refused with the protocol's not-found answer, identical to the answer for a path that does not exist, so a peer cannot tell hidden from missing (ADR-0006). | `ContentPathMapping.IsAnsweredAsAbsent`, set by `ContentStore` |
| escaped rendering | How the verbose log shows bytes: printable ASCII except backslash as itself, CR and LF as `\r` and `\n`, every other byte as `\xHH`, so no peer byte reaches the terminal as a control sequence (ADR-0006). | `ExchangeLogEscaping.AppendEscaped` in `Surl.Output.UnitLibrary` |

## HTTP

| Term | Meaning | Name in code |
| --- | --- | --- |
| request head | Everything an HTTP/1.x request sends before its body: the request line, then zero or more field lines, then the empty line that ends them (RFC 9112, sections 2.1 and 3). Empty lines before the request line are skipped (RFC 9112, section 2.2). Bounded by the request-head limit (ADR-0006). | `HttpRequestHead`, read by `HttpConnectionReader`, which reports how the read ended as an `HttpRequestHeadReadOutcome` |
| request line | The first line of a request head, `method SP request-target SP HTTP-version` (RFC 9112, section 3). | `HttpRequestHead.Method`, `HttpRequestHead.RequestTarget`, `HttpRequestHead.Version`; parsed by `HttpRequestLineParser` |
| field line | One header field in a request head, `field-name ":" OWS field-value OWS`, the whitespace around the value not part of it (RFC 9112, section 5). | `HttpRequestField`; parsed by `HttpFieldLineParser`; a head's field lines are `HttpRequestHead.Fields` |

## FTP

| Term | Meaning | Name in code |
| --- | --- | --- |
| control connection | The connection an FTP exchange is served on: the greeting, curl's command lines and the server's numbered replies (RFC 959). It is the exchange's connection; no file byte travels on it (ADR-0052 decision 1). | the exchange's `IConnection`, served by `FtpProtocolServer`; its lines read by `FtpLineReader` and answered by `FtpCommandResponder` |
| data connection | A second connection an FTP exchange opens for one transfer - `RETR`, `STOR`, `APPE`, `LIST`, `NLST` or `MLSD` - and closes after it. It belongs to its exchange: it is not counted against the connection limits, its bytes restart the exchange's idle clock and appear in the exchange's verbose and trace logs, and the notes `Data connection opened: ...` and `Data connection closed.` mark it. At most one at a time per exchange (ADR-0052 decisions 6 and 9). | an `IConnection` from the exchange's `ExchangeContext.DataConnections`; wrapped per exchange by `ExchangeDataConnections` in `Surl.Core.UnitLibrary`; kept per control connection by `FtpDataConnections` |
| data-connection opener | The seam through which a protocol server gets data connections without constructing a transport: it starts a passive listener or makes an active connection. Only `Surl.Networking` implements it over sockets; the default refuses every request (ADR-0052 decision 9). | `IDataConnectionOpener` in `Surl.Protocol.Abstractions`; `SocketDataConnectionOpener` in `Surl.Networking.UnitLibrary`; `RefusingDataConnectionOpener` (the default); `InMemoryDataConnections` in tests; a failure is a `DataConnectionException` carrying a `DataConnectionFailure` |
| passive mode | curl connects to surl for the data connection: `EPSV` (answered `229`) or `PASV` (answered `227`, IPv4 only). surl listens on the control connection's local address on an ephemeral port and accepts one connection, only from the control connection's peer address, within the head timeout (ADR-0052 decision 6). curl's default; `--disable-epsv` makes it send `PASV`. | `IDataConnectionOpener.StartPassiveListenerAsync`, returning an `IPassiveDataListener` |
| active mode | surl connects to curl for the data connection: `EPRT` or `PORT` (curl's `-P`/`--ftp-port`; `--disable-eprt` makes it send `PORT`) names the target, which must be the control connection's peer address and a port of 1024 or above, else `501` (ADR-0052 decision 6, RFC 2577). | `IDataConnectionOpener.ConnectActiveAsync`; the target parsed by `FtpActiveTargetParser` |
| explicit FTPS | TLS started on an `ftp://` control connection by `AUTH TLS` (or `AUTH SSL`), answered `234` and only when surl has a certificate (`--cert` or `--self-signed`), otherwise `534`; curl asks with `--ssl-reqd`, `--ssl` or `--ftp-ssl-control` (ADR-0052 decision 5). | `FtpProtocolServer`'s constructor argument `isAuthTlsAvailable`; the upgrade is `IConnection.UpgradeToTlsAsync` |
| implicit FTPS | FTP on an `ftps://` listen URL: the engine completes the TLS handshake before the greeting, as for `https://`, and data connections are protected from the start (ADR-0052 decision 5). | the `ftps` scheme, claimed by `FtpProtocolServer` itself |
| protection level (FTPS) | Whether an FTPS exchange's data connections are TLS: `PROT P` (private) or `PROT C` (clear), accepted after `PBSZ`; `C` by default on `ftp://` and `P` on `ftps://`. Under `P` each data connection is upgraded to TLS after its `150` reply, a fresh handshake with no session resumption required (ADR-0052 decision 5). | `FtpDataConnections.ProtectAsync` |

## SSH, SCP and SFTP

| Term | Meaning | Name in code |
| --- | --- | --- |
| SSH server | The one protocol server that answers both `scp://` and `sftp://` listen URLs: the SSH transport (RFC 4253), user authentication (RFC 4252) and the connection protocol (RFC 4254), with SCP and the SFTP subsystem run on its session channels (ADR-0051, ADR-0054). | `SshProtocolServer` in `Surl.Protocol.Ssh.UnitLibrary`; its help category and AI help topic are `ssh` |
| host key | A private key the SSH server proves its identity with by signing each key exchange, and whose public blob curl pins with `--hostpubsha256`, `--hostpubmd5` or `known_hosts`. Given by `--hostkey <file>` (repeatable, at most one per key type: RSA of at least 2048 bits, ECDSA on P-256, P-384 or P-521, Ed25519; an OpenSSH, PKCS #8, PKCS #1 or SEC 1 file, `--pass` for an encrypted one), read before any listener binds. An `scp` or `sftp` listen URL with no host key is refused with 2 (ADR-0051 decision 4). | `SshHostKey`, held in an `SshHostKeySet`; a file read by `SshHostKeyFile.Read`, refused as an `SshHostKeyRefusal`; `SurlCommandLine.HostKeyFiles`; composed by `SshHostKeyComposition` in `Surl.Console` |
| throwaway host key | The RSA 3072-bit host key `--throwaway-hostkey` makes in memory at start, only when an `scp` or `sftp` listen URL is served and no `--hostkey` is given; a loosening option with its startup warning carrying the key's `--hostpubsha256` value, since a client must pin it or skip the check (`curl -k`) (ADR-0051 decision 4). The SSH counterpart of the throwaway certificate. | `SurlCommandLine.ThrowawayHostKey`; `SshHostKeyComposition.ThrowawayHostKey` |
| host-key note | The verbose line `* Serving SSH host key <key type>, --hostpubsha256 <base64> --hostpubmd5 <hex>` surl writes for each host key served, before the listener status lines, so each value can be pasted after the curl option it follows (ADR-0051 decision 8 and Amendment 1). | `SshHostKeyComposition.FormatHostKeyNote`, written by `SshHostKeyComposition.WriteStartLines` |
| algorithm offer | The lists of key exchange methods, host-key algorithms, ciphers, MACs and compression methods the SSH server's `KEXINIT` sends, in surl's order of preference; the host-key list holds only the algorithms of the host keys held. curl's own order picks each algorithm (RFC 4253 section 7.1), and the verbose note `SSH negotiated ...` records what was agreed (ADR-0051 decisions 2 and 10). | `SshAlgorithmOffer` (`SshAlgorithmOffer.Default`); what is agreed is `SshNegotiatedAlgorithms` |
| weak SSH algorithm | An SSH algorithm built on SHA-1, MD5, CBC, RC4, 3DES, Blowfish, CAST-128, RIPEMD-160 or 1024-bit Diffie-Hellman, in the offer only when it is built with weak algorithms allowed, which also admits RSA keys shorter than 2048 bits and DSA keys (ADR-0051 decisions 2 and 2.3, ADR-0061). The option that asks for them, `--allow-weak-ssh-algorithms`, is parsed, but a start that gives it ends with `surl: (2) --allow-weak-ssh-algorithms is not available in this build`, so `surl` offers none of them today. | `SshAlgorithmOffer.AllowsWeakAlgorithms`, set by `SshAlgorithmOffer.Default`'s `allowWeakAlgorithms`; `SurlCommandLine.AllowWeakSshAlgorithms`; refused by `CommandLineRunner.FindUnavailableOption` |
| strict key exchange | OpenSSH's defence against the Terrapin attack (CVE-2023-48795): surl always lists its marker, and when curl's first `KEXINIT` lists the client marker the first key exchange admits no other message and each direction's sequence number restarts at 0 after every `NEWKEYS` (ADR-0051 decisions 2.1 and 2.2). | `SshAlgorithmOffer.StrictKeyExchangeServerMarker` (`kex-strict-s-v00@openssh.com`), `SshAlgorithmOffer.StrictKeyExchangeClientMarker` |
| key re-exchange | A key exchange after the first, on a connection already under keys: started by the client's `KEXINIT`, or by surl once either direction has carried 1 GiB or an hour has passed under one set of keys, checked between the client's packets (ADR-0051 decisions 2.1 and 2.2, ADR-0060). | `SshReExchangeLimits`; run by `SshTransportHandshake` |
| session channel | An RFC 4254 `session` channel on a logged-in SSH connection, on which one `exec` of an SCP command or one `sftp` subsystem runs; at most 10 open per connection, each with a 2 MiB window (ADR-0051 decision 9, ADR-0054 decision 2). | `SshSessionChannel`, opened by `SshConnectionProtocol` (`MaxOpenChannels`); what runs on it is an `ISshChannelHandler` |
| SCP command | The `exec` request that means SCP: exactly `scp <options> [--] <path word>`, options from `f`, `t`, `p`, `d`, `v` with exactly one of `-f` (source mode: surl sends one file, curl's download) and `-t` (sink mode: surl receives one file, curl's upload). No shell runs; any other command, `-r` included, is `CHANNEL_FAILURE` (ADR-0054 decisions 2 to 4). | `SshScpCommand`; source mode `ScpDownloadHandler`, sink mode `ScpUploadHandler` |
| SFTP subsystem | The `sftp` subsystem request on a session channel, answered as SFTP version 3 (draft-ietf-secsh-filexfer-02) through the content store: reads, stats, directory listings (with `--list-directories`), writes and tree changes (with `--allow-uploads`), and each of curl's `-Q` commands; at most 100 open handles per session (ADR-0054 decisions 5 to 11). | `SftpSession` (`MaxOpenHandles`) |
| hand-built primitive library | A `Surl.Cryptography.<Name>.UnitLibrary` holding one cryptographic primitive the base class library lacks, bytes in and bytes out, one of the horizontal libraries of ADR-0002 decision 3's table: `Curve25519`, `Ed25519`, `ChaCha20`, `Poly1305` (ADR-0048), `Rc4`, `BcryptPbkdf` (ADR-0051 decision 3), `Blowfish`, `Cast128`, `Ripemd160` (ADR-0061). How each composes into SSH stays in `Surl.Protocol.Ssh` (ADR-0048 decision 3). | `X25519`, `Ed25519`, `ChaCha20`, `Poly1305`, `Rc4`, `BcryptPbkdf`, `Blowfish`, `Cast128`, `Ripemd160` and `HmacRipemd160`, one library each (the last two share `Surl.Cryptography.Ripemd160`) |

## Authentication

| Term | Meaning | Name in code |
| --- | --- | --- |
| account | A user name and password surl accepts a login for, given by `-u`/`--user <user:password>` (repeatable, split at the first `:`) or by a line of the user file. An account with the empty user name holds a Bearer token and is matched by Bearer only. With no account configured every login is refused (ADR-0032 sections 1 and 2). | `Account` and `AccountBook` in `Surl.Authentication.UnitLibrary`; a `--user` value is a `CommandLineAccount` in `SurlCommandLine.Accounts` |
| user file | The file `--user-file <file>` names: UTF-8, one `user:password` account per line, blank lines and `#` lines skipped, passwords in clear. Read when surl starts serving, before any listener binds; its accounts come after every `--user` account (ADR-0032 section 2). | `SurlCommandLine.UserFile`; parsed by `UserFileParser`, a refused line a `UserFileLineFailure` |
| anonymous read | An HTTP `GET` or `HEAD` served with no login, which is allowed only while no account is configured. Once any account is, every HTTP request needs a login; every other HTTP method and every MQTT `CONNECT` always needs one (ADR-0032 sections 4 and 5). | `HttpAuthenticationRequest.IsWrite` (`false` for `GET` and `HEAD`), judged by `HttpAuthenticationSession` |
| authentication method | One HTTP scheme surl can check, named by its `--auth` word: `negotiate`, `ntlm`, `digest`, `basic`, `bearer`, `aws-sigv4`, listed in that order everywhere. The default set is `basic,bearer,digest,aws-sigv4`; `--auth` replaces it (ADR-0032 section 3). | `AuthenticationMethod`; `AuthenticationMethods.DefaultAccepted`; the set in force `AuthenticationSettings.AcceptedMethods`; each method an `IHttpAuthenticationMethod` |
| authentication policy | What judges every login - an HTTP request's `Authorization`, an MQTT `CONNECT`'s or an FTP `USER`/`PASS` pair's user name and password - against the accounts, the accepted methods and the loosening options. Protocol servers receive it through Abstractions and never reference `Surl.Authentication` (ADR-0032 section 6). | `IAuthenticationPolicy` in `Surl.Protocol.Abstractions`, implemented by `AuthenticationPolicy`; composed by `AuthenticationComposition` in `Surl.Console` |
| SSH authentication policy | What judges an SSH login once the SSH server has framed it and, for a signed public key, verified the signature: `none` (accepted only under `--allow-anonymous`), a password or keyboard-interactive answer against the accounts, a public key against the authorized keys. A separate interface beside the authentication policy, implemented by the same object (ADR-0051 decision 7). | `ISshAuthenticationPolicy` in `Surl.Protocol.Abstractions` (`SshNoneLogin`, `SshPasswordLogin`, `SshPublicKeyLogin`, answered by an `SshLoginVerdict`), implemented by `AuthenticationPolicy` |
| authorized key | A public key a user may log in to the SSH server with: one line of an OpenSSH `authorized_keys` file named by `--authorized-keys <user:file>` (repeatable, split at the first `:`), matched by the SHA-256 of its exact key blob, compared in fixed time. Key options before the key type are refused at start, not ignored (ADR-0051 decision 6). | `AuthorizedKey` and `AuthorizedKeyBook` in `Surl.Authentication.UnitLibrary`, parsed by `AuthorizedKeysParser`; an option value is a `CommandLineAuthorizedKeys` in `SurlCommandLine.AuthorizedKeys` |
| plain-text secret | A secret a passive listener reads straight off the wire: an HTTP Basic password, a Bearer token, an MQTT `CONNECT` password, an FTP `PASS`. Over an unencrypted connection it is refused unchecked - HTTP `403 Forbidden`, MQTT `CONNACK` 5, FTP `530 Login needs TLS first: send AUTH TLS` - unless `--allow-plaintext-auth` is given (ADR-0052 decision 3). Digest, NTLM, Negotiate and AWS Signature Version 4 send a value computed from the secret, so they are not plain-text (ADR-0032 section 3); an SSH password is sent only after the transport is encrypted, so it is not plain-text either (ADR-0051 decision 6). | `AuthenticationMethods.SendsPlaintextSecret`; refused as `PasswordLoginVerdict.RefusedPlaintext` or `HttpAuthenticationOutcome.Forbidden` |
| refusal delay | The fixed 1 second every refused credential waits, on the injected `TimeProvider`, before it is answered; missing credentials and a handshake's continuation step are not delayed (ADR-0032 section 8). | `AuthenticationPolicy.RefusalDelay` |
| loosening option | One of the five options that loosen a secure default for tests: `--allow-anonymous`, `--allow-plaintext-auth`, `--auth <methods>`, `--self-signed` and `--throwaway-hostkey`. Each writes a startup warning, none is on by default, and there is no umbrella option; `surl --help testing` explains each (ADR-0032 sections 1 and 9, ADR-0034 decision 5, ADR-0051 decision 11). | `SurlCommandLine.AllowAnonymous`, `.AllowPlaintextAuthentication`, `.GivenAuthenticationMethods`, `.SelfSigned`, `.ThrowawayHostKey`; its help paragraph is `OptionHelp.Explanation` |
| startup warning | A `surl: warning: <option>: ...` line a loosening option writes on every start, after the command line is read and before any listener status line, in the order `--allow-anonymous`, `--allow-plaintext-auth`, `--auth`, `--self-signed` (only when the throwaway certificate is made), `--throwaway-hostkey` (only when the throwaway host key is made). Written to the log stream from the `info` log level up (ADR-0032 section 9, ADR-0033 section 7, ADR-0051 decision 11). | `AuthenticationComposition.WriteLooseningWarnings`; the `--self-signed` line by `CommandLineRunner`; the `--throwaway-hostkey` line by `SshHostKeyComposition.WriteStartLines` |
| throwaway certificate | The self-signed server certificate surl makes at start for a listen URL that is TLS from the first byte, only when `--self-signed` is given and `--cert` is not; clients must skip verification (`curl -k`). Without either option such a listen URL ends surl with 58 before any listener binds, and `--self-signed` with `--cert` is refused (ADR-0032 section 10, superseding ADR-0010's default). | `ThrowawayServerCertificate` in `Surl.Networking.UnitLibrary`, made by `ServerTlsComposition` in `Surl.Console`; its fingerprint `ServerTlsComposition.ThrowawayCertificateFingerprint` |
| checked login | A login whose credentials were checked against the accounts, accepted or refused, and the only kind the verbose log notes: `Login accepted: <method> <user>` or `Login refused: <method> <user>`, `<method>` the HTTP `Authorization` scheme, the SSH method name as on the wire (`password`, `keyboard-interactive`, `publickey`; ADR-0051 decision 7) or otherwise the listen URL's scheme (`ftp`, `ftps`, `mqtt`, ...), `<user>` as sent (`bearer token` for Bearer, left out when unreadable). No credentials, a plain-text secret refused unchecked, no user name, a handshake's continuation step and `--allow-anonymous` are not checked logins (ADR-0032 section 8, ADR-0038). | `CheckedLogin` in `Surl.Protocol.Abstractions`, on `HttpAuthenticationVerdict.CheckedLogin`; a password login unchecked under `--allow-anonymous` is `PasswordLoginVerdict.AcceptedUnchecked` |

## Logging

| Term | Meaning | Name in code |
| --- | --- | --- |
| log level | How much surl logs, one of five in order: `none` (`-s`), `error` (`-s -S`), `info` (the default), `verbose` (`-v`) and `trace` (`--trace`, `--trace-ascii`), or any of them by `--log-level <level>`; the last level option given wins and `-S` is applied after the whole command line is read. Each level writes what the one before it writes, the per-exchange lines in the chosen level's form only (ADR-0033 sections 1 and 2). | `LogLevel` in `Surl.Output.UnitLibrary`; `SurlCommandLine.LogLevel` |
| log stream | Where the startup warnings, the throwaway-certificate note and the exchange log below the `trace` level go: stderr, or the `--log-file` file, appended, `-` meaning stdout. The `surl: (N)` failure messages and command-line refusals always go to stderr, never to the log stream (ADR-0033 sections 1 and 6). | `LogStreams.Log` in `Surl.Console`; the file `SurlCommandLine.LogFile`, opened by `LogFile.Open` |
| info line | What the `info` log level writes per exchange: the engine's `Exchange <id> opened: ...` note when the exchange opens, and its notes that tell of trouble (`cancelled`, `TLS handshake failed`, a protocol server that threw), each as the verbose exchange log writes it; nothing for bytes or a normal close (ADR-0033 section 3). | `LevelledExchangeLogFactory` at `LogLevel.Info`, whose logs are `NoteFilteringExchangeLog` |
| trace dump | What the `trace` log level writes: curl's `--trace` layout turned to the server's side, `#<id> <= Recv data, <n> bytes (0x<n>)` and `#<id> => Send data, ...` header lines, each followed by rows of hex and characters (`--trace`) or of characters only (`--trace-ascii`). Written to the trace file (truncated at start, `-` for stdout), or to the log stream by `--log-level trace` alone (ADR-0033 section 4). | `TraceExchangeLogFactory`, `TraceExchangeLog`, `TraceDumpRows` and `TraceDumpLayout` (`HexAndAscii`, `Ascii`) in `Surl.Output.UnitLibrary`; the file `SurlCommandLine.TraceFile`, opened as `LogStreams.Trace` |
| trace time stamp | The local time, `HH:mm:ss.ffffff` and a space, that `--trace-time` puts before every exchange log line and every trace dump header and note line, from the injected `TimeProvider`; dump rows, status lines, warnings and messages are not stamped (ADR-0033 section 5). | `SurlCommandLine.TraceTime`; `VerboseExchangeLog.TimestampFormat` |

## Help

| Term | Meaning | Name in code |
| --- | --- | --- |
| help subject | What follows `-h`/`--help`: nothing (the short list), `all`, `category`, a help category, or an option (its option page). An unknown category gets curl's `Unknown category provided` answer, an option name that names no option the `Incorrect option name` line; every help answer exits 0 at every log level (ADR-0034 decisions 3 and 4). | `CommandLineParseResult.HelpSubject`; answered by `HelpText.Answer` as a `HelpAnswer` |
| help category | A named group of options that `surl --help <category>` lists: `auth`, `content`, `limits`, `logging`, `security`, `surl`, `testing`, `tls`, and one per protocol family served (`dict`, `ftp`, `gopher`, `http`, `imap`, `mqtt`, `pop3`, `smtp`, `ssh`, `telnet`, `tftp`) (ADR-0034 decision 1). `ssh` covers `scp` and `sftp` and takes curl's own category name for them (ADR-0051 decision 12). Each is also an AI help topic of the same name. | `HelpCategory`, listed in `HelpCategories.All`; an option's are `OptionHelp.Categories` |
| short list | The options `surl --help` with no subject lists, before the pointer lines to the categories (ADR-0034 decision 2). | `OptionHelp.IsInShortList` |
| option page | What `surl --help <option>` writes: the option's left side, its description and default, for a loosening option its explanation, and its categories (ADR-0034 decision 3). | `HelpText.Answer`, from the option's `OptionHelp` |
| manual | The long text `-M`/`--manual` writes: the deployment checklist, the data directory, in-memory mode, accounts, the loosening options, the log levels, the limits and the exit codes (ADR-0034 decision 6). | `ManualText.Text`; `CommandLineOutcome.ShowManual` |
| AI help | What `surl --aihelp [topic]` writes: Markdown for an AI agent learning to call surl, on stdout, exit 0, at every log level. With no topic (or an empty one) the overview - what surl is, how a command line is built, how to read the pages, and the topic list; with an AI help topic that topic's page; with `all` the overview then every topic page; with anything else, an option included, the unknown-topic answer, which lists the topics. Its option and exit-code tables are generated from the option table, so they cannot drift from `--help`. A deliberate addition with no upstream curl equivalent, and not a mode of `--help` (ADR-0046). | `AiHelpText.Answer`, returning a `HelpAnswer`; parsed as `CommandLineOutcome.ShowAiHelp` with `CommandLineParseResult.AiHelpTopic`; the option kind `CommandLineOptionKind.AiHelp` |
| AI help topic | What follows `--aihelp`: one page of AI help, always with the sections About, Schemes, Options, Exit codes and Examples. Every help category is an AI help topic of the same name and description, and two topics are added beside them: `exit-codes` and `listen-urls`. A help category is a group of `--help` options; an AI help topic is a page, and not every topic is a category. Matched in any case (ADR-0046 decision 3). | `AiHelpTopic`, listed in `AiHelpTopics.All`, found by `AiHelpTopics.TryFind`; a protocol topic's schemes are `HelpCategory.Schemes` |
| AI help example | One exact `surl` command line on an AI help page, with its precondition, every stdout and stderr line, its exit code and the upstream curl command lines that reach it; `Surl.Console.UnitTests` runs each and compares (ADR-0046 decision 7). | `AiHelpExample`, `AiHelpExamplePrecondition`, listed in `AiHelpExamples.All` |
| argument type | The kind of argument an option takes and the values its reader accepts, as the AI help option table shows them (`seconds`, `bytes`, `word`, `flag` and the rest) (ADR-0046 decision 5). | `OptionArgumentType` (`Name`, `AllowedValues`), paired with its reader by `OptionArgumentReading<T>`; `CommandLineOption.ArgumentType` |
| exit-code guidance | For each `SurlExitCode` member, when surl returns it, what an agent should do next, and the AI help topics that list it (ADR-0046 decision 6). | `ExitCodeGuidance`, one row per member in `ExitCodeGuidanceTable.All` |
