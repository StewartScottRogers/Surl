# Glossary

One term, one meaning, one name in code. When code or a document uses one of these
terms, it means exactly what is written here; when a concept below needs naming in code,
it uses the name in the "Name in code" column. "Not yet" means Phase 1 or later names it.

## Two programs named curl

| Term | Meaning | Name in code |
| --- | --- | --- |
| upstream curl | The original C implementation of curl, https://github.com/curl/curl. Surl's only oracle (ADR-0003). Always "upstream curl" when the distinction matters. | — |
| the Curl port | Stewart's C# port of curl, https://github.com/StewartScottRogers/Curl. Measured against Surl in the last phase; never used to validate Surl (ADR-0003). Always "the Curl port", never bare "Curl" when it could be misread. | — |
| pinned upstream build | An upstream curl executable identified by its SHA-256 in `UpstreamCurlBuilds.json`. The only kind of curl Surl's tools run. | `UpstreamCurlBuilds.json`, `Assert-PinnedUpstreamCurl` |
| reference release | The upstream curl release Surl is measured against: 8.21.0, released 2026-06-24, the release the Curl port targets. | — |
| original protocol | A protocol upstream curl speaks, served by a `Surl.Protocol.<Name>` server and measured only against pinned upstream curl (ADR-0003). | `Surl.Protocol.*` |
| extended protocol | A protocol the Curl port adds beyond upstream curl, listed in the port's `Documentation/Protocols.md`, "Extended protocols" (S3, Redis, MQTT 5 and the rest). Judged by its own specification, not by upstream curl (ADR-0083). | — |
| extended server | The Surl server for one extended protocol, `Surl.Extended.Protocol.<Name>`. Isolated from the original servers, turned off with every other extended server by `SURL_EXTENSIONS=0`; the Curl port's pinned client may run against it only in `Integration` tests, never as proof (ADR-0083). | `Surl.Extended.Protocol.*`, `SURL_EXTENSIONS` |
| Curl port client pin | The Curl port's `curl` executable identified by its SHA-256 (and the port commit it was published from) in `CurlPortBuilds.json`, the only port binary an extended server's integration test runs. Never listed in `UpstreamCurlBuilds.json`. | `CurlPortBuilds.json` |
| Phase 7 | The last phase: the Curl port runs the same conversations against Surl beside pinned upstream curl, and every disagreement is written down as a Phase 7 finding (ADR-0003 decision 6, ADR-0089). The port is the thing measured, never the oracle. | `CurlPortBesideUpstreamCurlOver<Family>Tests` in `Surl.Conformance.UnitTests` |
| port defect | The Phase 7 verdict for a case where upstream curl's run is what the mirrored conformance test asserts and the Curl port's run differs in a compared item after normalisation (ADR-0089 decisions 4 and 5). Filed on the port's board through the handoff, never fixed by changing Surl. Where upstream's own run fails instead, the verdict is a Surl defect, filed on Surl's board. | `CurlPortVerdict`, `CurlPortVerdictKind` |
| Phase 7 finding | The written record of one port defect, in `Documentation/Conformance/CurlPort/<Family>.md`: the test and the test it mirrors, the command line, both results where they differ, and the specification or upstream documentation that says which is right, under the port commit, upstream builds and Surl commit measured (ADR-0089 decision 6). A Phase 7 test fails when a finding appears unlisted or a listed one disappears. | `CurlPortFinding` |
| mirrored test | The original-protocol conformance test (a `UpstreamCurl…SurlOver…Tests` method or a runnable upstream test case) whose conversation a Phase 7 case repeats with the Curl port's client, and whose assertions decide whether upstream's own run was right (ADR-0089 decision 1). | `CurlPortMeasurementCase.Mirrors` |
| not comparable | The Phase 7 verdict for a case whose two runs differ for a named reason that is not the port's, such as a release difference between the port's target and the pinned upstream build. Counted apart from agreements and port defects. | `CurlPortVerdictKind.NotComparable` |
| Phase 7 handoff | `Documentation/Conformance/CurlPort/Port-Board-Handoff.md`: the Phase 7 findings written as tasks in the port's own task shape, for Stewart to file on the port's board. No Surl session writes into the port's repository (ADR-0089 decision 7). | `Port-Board-Handoff.md` |

## Serving

| Term | Meaning | Name in code |
| --- | --- | --- |
| mate | The server that answers a given curl request. Surl is curl's mate. | — |
| listen URL | A URL given to `surl`: its scheme picks the protocol server, its host and port the bind address. | `ListenUrl` (ADR-0004) |
| protocol server | The library that answers one protocol family, secure variants included: `Surl.Protocol.<Name>.UnitLibrary`. | `IProtocolServer`, implemented through `IConnectionProtocolServer` or `IDatagramProtocolServer` (ADR-0004) |
| horizontal library | A library a protocol server may reference besides Abstractions, listed in ADR-0002's table. | `HorizontalLibraries` in `ProtocolIsolationTests` |
| server composition | Building every protocol server a host registers - the original servers, their implicit-TLS second registrations and the extended servers behind `SURL_EXTENSIONS` - with the content store, the service state they keep across connections and the connection limits. Done in one library every host calls, so `surl` and the planned `Surl.Api` cannot drift (ADR-0099 decision 1). A composition root - `Surl.Console`, `Surl.Composition`, `Surl.Api`, `Surl.Mcp` - is referenced by no protocol server or horizontal library (ADR-0099 decision 11). | `SurlServerComposition` in `Surl.Composition.UnitLibrary` (`ComposeProtocolServers`, `ExtendedProtocolServers.Compose`, `ServiceState`) |
| data directory | The directory `--directory` names: its files are what every file-serving protocol server serves, and its `.surl` folder holds every other kind of service state, both surviving restarts. Without `--directory` there is none: surl serves an empty in-memory file system and keeps service state in memory (ADR-0031 decision 1, superseding ADR-0007's default of the current directory). Formerly "served directory". | `SurlCommandLine.DataDirectory` (`null` without `--directory`) |
| served root | The full path the content store is rooted at: the data directory's full path with `--directory`, `InMemoryContentFileSystem.RootPath` without it (ADR-0031 decision 1, ADR-0018). | `ContentStore.ServedRoot` |
| in-memory file system | The file system the content store serves without `--directory`: empty at start, lasting for the process lifetime, bounded by `InMemoryContentFileSystem.DefaultMaxTotalBytes` (256 MiB) and never touching the disk. Past the bound a write fails as on a full disk (ADR-0031 decision 4). The second `IContentFileSystem` implementation beside `DiskContentFileSystem`. | `InMemoryContentFileSystem` |
| service-state folder | `<data directory>/.surl`: where services keep state other than served files (`.surl/bus` for the message bus, whose `retained` file replaced the MQTT-only `.surl/mqtt/retained-messages`, which an older data directory still has and `surl` still reads once; `.surl/mail` for the mail store) and where the data-directory lock lives. Never served, listed or uploaded to, whatever `--serve-dot-files` and `--follow-symlinks` say; the match is the first path segment, case-insensitive (ADR-0031 decisions 5 and 6). | `DataDirectoryLock.StateFolderName` in `Surl.Composition`; hidden by `ContentStore` |
| data-directory lock | `<data directory>/.surl/lock`, held open exclusively for as long as surl serves, so one surl process uses a path at a time. A second process given the same path gets `DataDirectoryInUse` (124); a `.surl` or lock file that cannot be created gets `CouldNotWriteFile` (23). The operating system releases it when the holder exits; the file is never deleted (ADR-0031 decision 7). | `DataDirectoryLock.Take` in `Surl.Composition`, returning a `DataDirectoryLockOutcome` |
| listener status line | The line `Listening on <scheme>://<host>:<bound port>/` surl writes to stdout for each listen URL once every listener has bound, from the `info` log level up, so `-s` and `-s -S` write none (ADR-0007, ADR-0033 section 1). | `ListenerStatusLine` in `Surl.Output.UnitLibrary` |
| verbose exchange log | What the `verbose` log level (`-v`) writes to the log stream: one line per exchange event, `#<exchange id> <marker> <text>`, the marker `<` for bytes received, `>` for bytes sent, `*` for a note (ADR-0007 section 8, ADR-0033 section 1). | `IExchangeLog`, `IExchangeLogFactory` (ADR-0004); `LevelledExchangeLogFactory` at `LogLevel.Verbose`, whose logs are `VerboseExchangeLog`, in `Surl.Output.UnitLibrary` |
| parsed command line | What `Surl.Cli` returns for a command line that serves: the listen URLs and every option value, defaults applied (ADR-0007). | `SurlCommandLine` |
| negatable option | A flag that `--no-<name>` turns off, as curl's boolean options are; the later of the two wins (ADR-0007). | `CommandLineOption.Negatable` in `Surl.Cli.UnitLibrary` |
| content store | The file tree under the served root that every file-serving protocol server publishes, read and written through an `IContentFileSystem`, and the rules that map request paths onto it without escaping it. | `ContentStore` in `Surl.Content.UnitLibrary` |
| exchange | One conversation between upstream curl and Surl, over one connection or one datagram flow, from accept to close. One `ServeAsync` call. | `ExchangeContext` (ADR-0004) |
| hardening limit | A bound on what a peer can make Surl hold - connections, time, bytes - with a default number, an option to change it, and 0 meaning no limit (ADR-0006). | `ExchangeLimits` for the per-exchange ones, `ConnectionLimits` in `Surl.Core.UnitLibrary` for the connection-level ones |
| idle timeout | How long an exchange may go with no byte moving in either direction on any of its transports before Surl closes it. 120 s by default (ADR-0006). | `ConnectionLimits.IdleTimeout` in `Surl.Core.UnitLibrary` |
| head timeout | How long a peer has to deliver a complete request head, command line or first packet; the slow-sender defence. 30 s by default (ADR-0006). | `ExchangeLimits.HeadTimeout` |
| connection refusal | The protocol's own "too busy" answer written to a connection or datagram flow accepted past a connection limit, before it is closed (ADR-0006). | `IConnectionRefusalWriter`, `IDatagramRefusalWriter`, `ConnectionRefusal` |
| exposure default | What a server offers until an option says otherwise: uploads, directory listings, symbolic links, dot-files. All off by default (ADR-0006). | `ContentExposureOptions` in `Surl.Content.UnitLibrary` |
| answered as absent | Refused with the protocol's not-found answer, identical to the answer for a path that does not exist, so a peer cannot tell hidden from missing (ADR-0006). | `ContentPathMapping.IsAnsweredAsAbsent`, set by `ContentStore` |
| escaped rendering | How the verbose log shows bytes: printable ASCII except backslash as itself, CR and LF as `\r` and `\n`, every other byte as `\xHH`, so no peer byte reaches the terminal as a control sequence (ADR-0006). | `ExchangeLogEscaping.AppendEscaped` in `Surl.Output.UnitLibrary` |
| implicit TLS scheme | A scheme that is TLS from the first byte: `https`, `wss`, `ftps`, `imaps`, `pop3s`, `smtps`, `ldaps`, `gophers`, `mqtts`, `smbs`. The engine completes the handshake before the protocol server's `ServeAsync`, and the server tells it apart by `IConnection.TlsSession`, never by the scheme. The HTTP, WebSocket, SMTP, IMAP, POP3 and LDAP servers claim only their plaintext scheme and are registered a second time for the secure one; the FTP server claims `ftps` itself, and the SMB server `smbs` (ADR-0010 section 2, ADR-0020). | `ListenUrl.IsImplicitTls`, which the engine reads and which defaults to `TlsSchemes.IsImplicitTls` of the scheme (BL-1020); the second registration is `ImplicitTlsSchemeServer` in `Surl.Composition` |
| TLS upgrade | TLS started part way through a plaintext connection by the protocol's own command: `STARTTLS` (SMTP, IMAP), `STLS` (POP3), `AUTH TLS` (FTP), the `StartTLS` extended operation (LDAP, ADR-0072 decision 5). Offered only when a certificate is configured (`--cert` or `--self-signed`, for which `--self-signed` then makes the throwaway certificate), and refused in the protocol's own words otherwise; bytes pipelined after the command are discarded before the handshake (ADR-0010 section 1). | `IConnection.UpgradeToTlsAsync`; whether it is offered is `isTlsUpgradeAvailable`, the one name from `SurlServerComposition.ComposeProtocolServers` (from `ServerTlsComposition.IsCertificateConfigured`) into every server's constructor - FTP, SMTP, IMAP and POP3 alike, and LDAP's through `SurlServerComposition.LoadLdapServerAsync` (ADR-0069) |

## Stand-in for tests

| Term | Meaning | Name in code |
| --- | --- | --- |
| stand-in | A real Surl server that someone else's integration test runs against in place of the real mail server, bucket, broker or file site, often several protocols in one instance, started in process through `Surl.Api` or as `surl` (root `CLAUDE.md`, "Surl is a stand-in for tests"; ADR-0124). | — |
| event stream | The one bounded stream per instance (one `surl` run, one `Surl.Api` server) on which every exchange's start, bytes and end, every judged login, every store change, every fault applied and every hook failure is published, in one order numbered by `Sequence`; recording, queries, `Surl.Mcp`, the control endpoint and hooks subscribe to it, and a slow subscriber loses its oldest events rather than slowing a server (ADR-0124 decision 1). | `ISurlEventPublisher`, `SurlEvent`, `SurlEventStream` (not yet: BL-823, BL-787) |
| fault rule | One instruction to misbehave on purpose - delay, drop, refuse-login, error or out-of-space - scoped by listener or scheme, account, path and command, applied a set number of times or always, given as a `--fault` item, a `Surl.Api` `SurlFault`, a `Surl.Mcp` tool or a control endpoint request, and held in the instance's fault plan (ADR-0124 decision 4). | `FaultRule`, `IFaultPlan`, `FaultPlan` (not yet: BL-823, BL-792) |
| snapshot | An opaque, bounded, in-memory copy of an instance's in-memory stores - mail, content, message bus, accounts (password hashes only) - that the same instance can restore; never taken of a `--directory` store (ADR-0124 decision 3). Not the IMAP view `MailboxSnapshot`. | `ComposedSnapshot`, `SurlSnapshot` (not yet: BL-805, BL-810) |
| control endpoint | The loopback-only HTTP and JSON endpoint `--control` turns on, guarded by the bearer token in `--control-token-file`, through which a test suite not written in .NET reads events and exchanges, adds fault rules and seeds, resets, snapshots and restores stores (ADR-0124 decision 7). | `Surl.Control`, `IControlTarget` (not yet: BL-814 to BL-816) |
| host | A program that starts Surl's protocol servers: `surl` (`Surl.Console`), the in-process `Surl.Api` and the MCP server `surl-mcp` (`Surl.Mcp`). Each is a composition root, keeps `surl`'s secure-by-default rules, and starts servers through the composition (ADR-0098). | `Surl.Console`, `Surl.Api`, `Surl.Mcp` |
| composition | The one start every host runs: it turns a parsed command line into the running protocol servers, the stores they share and the instance's event stream, so a default or a refusal is `surl`'s whichever host asks (ADR-0099). | `SurlServerComposition.ComposeAsync`, `ComposedServing`, in `Surl.Composition` |
| Surl.Api server | One in-process Surl instance a .NET test starts with `SurlServer.StartAsync(SurlServerOptions)` and stops with `StopAsync` or disposal; port 0 takes a free port, `BoundUrls` lists the listen URLs with their bound ports, and a start `surl` would refuse throws `SurlServerStartException` (ADR-0099). | `SurlServer`, `SurlServerOptions`, in `Surl.Api` |
| exchange record | What `Surl.Api` keeps of one exchange when `RecordExchanges` is on: its ID, the listen URL that accepted it with its bound port, its scheme, the client's endpoint, when it started, the chunks of bytes in the order they crossed, and whether it was truncated; the bytes the client sent are `Received` and the bytes the server answered are `Sent` (ADR-0099 decision 7, ADR-0124 decision 1). `get_exchanges` of `Surl.Mcp` returns the same facts. | `SurlExchangeRecord`, `SurlExchangeChunk`, in `Surl.Api` |
| MCP tool | One action an AI agent may call on `surl-mcp`: `start_server`, `list_servers`, `stop_server`, `get_exchanges`, `get_events`, `wait_for_event`, `seed_mail`, `put_file`, `publish_message`, `add_account`, `reset_server`, `snapshot_server`, `restore_server`, `add_fault`, `list_faults` or `remove_fault`. Each is registered by one explicit line, never found by scanning (ADR-0103 decision 3, ADR-0124 decision 8). | `McpTool` and `McpServerRegistry.AddTool`, in `Surl.McpServing`; the tools themselves in `Surl.Mcp.UnitLibrary` |
| MCP resource | A read-only document `surl-mcp` offers an agent: the `surl://aihelp` resources, which carry the pages of `surl --aihelp` (ADR-0103 decision 6). | `McpResource`, `IMcpResourceProvider`, in `Surl.McpServing`; `AiHelpResourceProvider`, in `Surl.Mcp.UnitLibrary` |

## HTTP

| Term | Meaning | Name in code |
| --- | --- | --- |
| request head | Everything an HTTP/1.x request - or an RTSP/1.0 one, which borrows its syntax - sends before its body: the request line, then zero or more field lines, then the empty line that ends them (RFC 9112, sections 2.1 and 3). Empty lines before the request line are skipped (RFC 9112, section 2.2). Bounded by the request-head limit (ADR-0006). | `HttpRequestHead`, read by `HttpConnectionReader`, which reports how the read ended as an `HttpRequestHeadReadOutcome`, all in `Surl.HttpMessage`; the HTTP and WebSocket servers read one with it, and so does the RTSP server's library (ADR-0070) |
| request line | The first line of a request head, `method SP request-target SP HTTP-version` (RFC 9112, section 3), or `RTSP/1.0` in place of the HTTP version (RFC 2326, section 6.1). | `HttpRequestHead.Method`, `HttpRequestHead.RequestTarget`, `HttpRequestHead.Version`, `HttpRequestHead.Protocol`; parsed by `HttpRequestLineParser` for the `HttpMessageProtocol` it is given, in `Surl.HttpMessage` |
| field line | One header field in a request head, `field-name ":" OWS field-value OWS`, the whitespace around the value not part of it (RFC 9112, section 5). | `HttpRequestField`; parsed by `HttpFieldLineParser`; a head's field lines are `HttpRequestHead.Fields`; in `Surl.HttpMessage` |
| request handler | What decides the answer to each HTTP request without writing it or asking which HTTP version carried it; the one shape an extended HTTP server implements (ADR-0084, decision 1). The HTTP server's is its answerer. | `IHttpRequestHandler`, handed an `HttpRequest` and returning an `HttpAnswer`, in `Surl.HttpServing`; `HttpRequestAnswerer` in `Surl.Protocol.Http` |
| HTTP/1.1 connection server | The loop that serves one HTTP/1.x connection for a request handler: reads each request head, refuses a malformed one, answers the rest through the handler, writes the answer, and keeps or closes the connection with the lingering close (RFC 9112; ADR-0084, decision 1). | `Http1ConnectionServer`, in `Surl.HttpServing` |
| connection takeover | What owns a connection after an HTTP/1.1 upgrade: the connection server writes the answer's `101 Switching Protocols` head, then hands the connection and its reader over, and writes or drains nothing after it (ADR-0084, decision 1). | `IHttpConnectionTakeover`, carried by `HttpAnswer.Takeover`, in `Surl.HttpServing` |

## HTTP/2

Decided by ADR-0081, ADR-0090 and ADR-0091, and built. The frames, streams and connection are in
`Surl.Http2` (ADR-0086 decision 1); HPACK is in `Surl.Hpack`; the HTTP server wires them to its
answering in `Surl.Protocol.Http`.

| Term | Meaning | Name in code |
| --- | --- | --- |
| HTTP/2 | The binary-framed version of HTTP (RFC 9113): many requests at once on one connection, each on its own stream, with compressed fields. Surl serves it on `https` when ALPN agrees `h2`, and on `http` by prior knowledge or `Upgrade: h2c` (ADR-0081). | `Http2ConnectionServer` in `Surl.Http2` serves a connection; `HttpProtocolServer` in `Surl.Protocol.Http` decides which connections it serves; `Http2StreamAnswerWriter` writes the answers |
| ALPN | TLS's Application-Layer Protocol Negotiation (RFC 7301): the client lists protocol IDs in its ClientHello and the server picks one, `h2` or `http/1.1` for HTTPS. | `TlsApplicationProtocols` in `Surl.Networking`; the agreed one is `TlsSession.ApplicationProtocol` |
| h2c | HTTP/2 over cleartext TCP, the `http` scheme's HTTP/2, reached by prior knowledge or by an `Upgrade: h2c` request answered `101 Switching Protocols`. Also the token in that `Upgrade` field. `h2` is HTTP/2 over TLS. | `Http2CleartextUpgrade` and `Http2CleartextUpgradeHandler` in `Surl.Protocol.Http` (the upgrade; ADR-0091) |
| prior knowledge | A client speaking HTTP/2 from its first byte, with no ALPN and no upgrade (`curl --http2-prior-knowledge`). | `HttpProtocolServer` reads the first bytes with `Http2ConnectionPreface` (ADR-0090) |
| connection preface | The 24 bytes every HTTP/2 client sends first, `PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n`, followed by its `SETTINGS`; the server's preface is its own `SETTINGS` frame (RFC 9113, section 3.4). How the `http` listener tells HTTP/2 from HTTP/1.x. | `Http2ConnectionPreface` in `Surl.Http2` |
| frame | HTTP/2's unit on the wire: a 9-byte header (24-bit length, type, flags, 31-bit stream identifier) and a payload, e.g. `HEADERS`, `CONTINUATION`, `DATA`, `SETTINGS`, `WINDOW_UPDATE`, `PING`, `RST_STREAM`, `GOAWAY` (RFC 9113, section 4). | `Http2Frame` and its types (`Http2DataFrame`, `Http2HeadersFrame`, `Http2SettingsFrame` and the rest), `Http2FrameType`, read by `Http2FrameReader` and `Http2FrameParser`, written by `Http2FrameWriter`, in `Surl.Http2` |
| stream | One request and its response on an HTTP/2 connection, identified by an odd number the client picks (stream 1 first, or the upgraded request); its life runs through the states of RFC 9113 section 5.1. | `Http2Stream` and `Http2RequestStream` in `Surl.Http2`; the handler is `IHttp2StreamHandler` |
| header block | The HPACK-compressed fields of one request or response: a `HEADERS` frame's block and the `CONTINUATION` frames after it, up to the one flagged `END_HEADERS`. Bounded by `--max-message` (ADR-0006). | `Http2HeadersFrame` and `Http2ContinuationFrame`, decoded by `HpackDecoder` into an `Http2RequestHead` (`Http2RequestHeadMapping`), in `Surl.Http2` |
| HPACK | HTTP/2's field compression (RFC 7541): a static table, a per-connection dynamic table, integer and string literals and a Huffman code. Hand-built, in its own horizontal library. | `Surl.Hpack`: `HpackDecoder`, `HpackEncoder`, `HpackDynamicTable`, `HpackStaticTable` and `HpackHuffman` |
| flow-control window | How many `DATA` bytes a peer may still send on a stream and on the connection; `WINDOW_UPDATE` widens it (RFC 9113, section 5.2). | `Http2SendWindows` and `Http2DataStream` in `Surl.Http2`; `Http2WindowUpdateFrame` |
| `GOAWAY` and `RST_STREAM` | The frames that end a whole HTTP/2 connection and one stream, each with an error code (`NO_ERROR`, `PROTOCOL_ERROR`, `REFUSED_STREAM`, `ENHANCE_YOUR_CALM`, `HTTP_1_1_REQUIRED`, ...). ADR-0081 decision 5 names the code each limit ends with. | `Http2GoAwayFrame`, `Http2RstStreamFrame` and `Http2ErrorCode` (`Http11Required` is `HTTP_1_1_REQUIRED`) in `Surl.Http2` |

## HTTP/3 and QUIC

Decided by ADR-0082 (with ADR-0096, ADR-0140 and ADR-0147), and built. QUIC is in `Surl.Quic`,
the TLS 1.3 handshake for it in `Surl.Tls13`, QPACK in `Surl.Qpack`, the HTTP/3 frames and
connection in `Surl.Http3` (ADR-0086 decision 2), and the HTTP server's HTTP/3 in
`Surl.Protocol.Http`.

| Term | Meaning | Name in code |
| --- | --- | --- |
| HTTP/3 | HTTP over QUIC (RFC 9114): each request on its own QUIC stream, fields compressed with QPACK. Surl serves it only with `surl --http3`, on UDP at the `https` listener's port; curl asks for it with `--http3` or `--http3-only`. | `Http3ProtocolServer` and `Http3ApplicationProtocol` in `Surl.Protocol.Http`, over `Http3ConnectionServer` in `Surl.Http3`; answers are written by `Http3StreamAnswerWriter` |
| QUIC | The UDP transport HTTP/3 runs on (RFC 9000): encrypted packets carrying frames, many streams on one connection, its own loss recovery and flow control, and TLS 1.3 built in (RFC 9001). Hand-built: Surl does not use `System.Net.Quic`. | `QuicServerConnection` (which does no I/O), carried over UDP by `QuicDatagramFlowLoop`, with `QuicApplicationConnection` for the application above it, in `Surl.Quic` |
| connection ID | The bytes at the start of a QUIC packet that name its connection; each side picks the ID the other puts on the packets it sends (Destination Connection ID, DCID; Source Connection ID, SCID). Surl's is 8 random bytes; curl's are 20. | `QuicConnectionIds` and `QuicPeerConnectionIds` in `Surl.Quic` |
| Initial packet | The first QUIC packets of a connection, sent at the Initial encryption level with keys anyone can derive from the client's DCID (RFC 9001 section 5.2); the client's carry its ClientHello in `CRYPTO` frames, padded to 1200 bytes. What `Record-CurlExchange.ps1 -QuicInitial` records. | `QuicLongHeaderPacket` with `QuicPacketType` Initial, and `QuicInitialSecrets`, in `Surl.Quic` |
| encryption level | One of QUIC's four sets of packet keys - Initial, 0-RTT, Handshake and 1-RTT (application data) - each derived from a different TLS 1.3 secret; Surl never accepts 0-RTT. | `TlsEncryptionLevel` in `Surl.Tls13` |
| packet number space | A sequence of packet numbers acknowledged on its own: Initial, Handshake and application data each have one (RFC 9000 section 12.3), so loss is detected per space. | `QuicPacketNumberSpace`, with `QuicLossDetection` and `QuicCongestionController` (ADR-0140), in `Surl.Quic` |
| packet protection | QUIC's encryption of a packet's payload with the level's AEAD (AES-GCM or ChaCha20-Poly1305) and of its header's packet number and flags with a mask (header protection), RFC 9001 section 5. | `QuicPacketProtection` with `QuicAesGcmPacketCipher` or `QuicChaCha20Poly1305PacketCipher`, in `Surl.Quic` |
| `CRYPTO` frame | The QUIC frame that carries TLS 1.3 handshake messages, at an offset, in place of TLS records; curl splits and repeats its ClientHello across many, so they are reassembled by offset. | `QuicCryptoFrame` and `QuicCryptoReassembly` in `Surl.Quic` |
| transport parameters | The settings each QUIC endpoint declares in its handshake, in TLS's `quic_transport_parameters` extension: flow-control credit, stream counts, idle timeout, connection IDs (RFC 9000 section 18). ADR-0082 decision 4 lists Surl's. | `QuicTransportParameters` in `Surl.Quic` |
| Version Negotiation | The packet a QUIC server sends to a client that asked for a version it does not speak, listing the versions it does; Surl lists only version 1. | `QuicVersionNegotiationPacket` and `QuicVersions` in `Surl.Quic` |
| TLS 1.3 for QUIC | The TLS 1.3 handshake (RFC 8446) without its record layer, its messages carried in `CRYPTO` frames and its secrets handed to QUIC per encryption level. Hand-built, because `SslStream` cannot hand out either. | `TlsServerHandshake` (with `TlsServerHandshakeOptions`, `TlsKeySchedule` and `TlsServerNegotiation`) in `Surl.Tls13` |
| HelloRetryRequest | The TLS 1.3 server's answer to a ClientHello with no key share for a group the server accepts: it names the group, and the client sends a new ClientHello with a share for it. | `ServerHello.HelloRetryRequest` in `Surl.Tls13`, chosen by `TlsServerNegotiation` |
| X25519MLKEM768 | The hybrid TLS 1.3 key-exchange group (`0x11EC`) that pairs ML-KEM-768 with x25519; every measured curl sends its key share first. | `TlsNamedGroup.X25519MlKem768` in `Surl.Tls13`, over `MlKem768` in `Surl.Cryptography.MlKem` and `Surl.Cryptography.Curve25519` |

## DTLS

Decided by ADR-0087; `Surl.Dtls` builds it for the `coaps` server.

| Term | Meaning | Name in code |
| --- | --- | --- |
| DTLS | Datagram TLS: TLS 1.2 adapted to run over UDP (RFC 6347), with an explicit epoch and sequence number on every record, a handshake that survives lost and reordered datagrams, and a cookie exchange against spoofed addresses. | flight | The handshake messages one side sends together and retransmits together (RFC 6347 section 4.2.4): the server's `ServerHello` to `ServerHelloDone`, or its final `ChangeCipherSpec` and `Finished`. | cookie exchange | The DTLS server's defence against spoofed source addresses (RFC 6347 section 4.2.1): a `ClientHello` without a valid cookie is answered with a `HelloVerifyRequest` carrying one, and nothing is kept until a hello returns with it. ## Shared stores and the configuration command line

Servers that do the same job share one store in one `surl` run (ADR-0100), and the layer-2
options configure what the stores hold (ADR-0101, ADR-0102). `surl --aihelp mail`,
`surl --aihelp messages`, `surl --aihelp content` and `surl --aihelp auth` list every option;
this section defines the terms only. Seeding, resetting and snapshotting the stores in a test
are described by the "Stand-in for tests" terms above; the wiki page that will explain them,
`Surl-As-A-Stand-In.md`, is BL-821's and does not exist yet.

| Term | Meaning | Name in code |
| --- | --- | --- |
| message bus | The one store of messages that the servers doing publish and subscribe share in one `surl` run, so a message published over `mqtt://` is seen over every other protocol registered on it. It holds live fan-out to matching subscriptions, one retained message per topic (only MQTT reads it), named queues with competing consumers, and an append-only log per topic. Bounded; persisted under `<data directory>/.surl/bus` with `--directory` (a malformed file ends surl with 37), in memory without. Registered on it today: `mqtt` and `mqtts` (whose retained messages moved onto it, BL-635), `nats` and `natss`, `stomp` and `stomps`. The `mqtt5`, `amqp`, `amqp1`, `kafka` and `redis` libraries are written against it but `surl` does not register them yet (BL-975, BL-507, BL-514, BL-973, BL-492). `mqtt5` keeps no retained messages of its own (ADR-0100 decision 3.9) (ADR-0100 decision 3). | `MessageBus` in `Surl.MessageBus.UnitLibrary` (not `Bus`); composed once per start by `SurlServerComposition.LoadServiceStateAsync` and `MessageBusComposition` |
| canonical topic | A message bus topic name: MQTT's topic name (non-empty UTF-8, at most 65535 bytes, no U+0000, no `+` or `#`, levels split at `/`). Digest, NTLM, Negotiate, AWS Signature Version 4, `CRAM-MD5`, `DIGEST-MD5` and `APOP` send a value computed from the secret, so they are not plain-text (ADR-0032 section 3, ADR-0049 section 1); an SSH password is sent only after the transport is encrypted, so it is not plain-text either (ADR-0051 decision 6). | `AuthenticationMethods.SendsPlaintextSecret`; refused as `PasswordLoginVerdict.RefusedPlaintext`, `SaslLoginOutcome.RefusedPlaintext` or `HttpAuthenticationOutcome.Forbidden`; not offered through `MailLoginOffer.IsClearPasswordLoginOffered` |
| refusal delay | The fixed 1 second every refused credential waits, on the injected `TimeProvider`, before it is answered; missing credentials and a handshake's continuation step are not delayed (ADR-0032 section 8). | `AuthenticationPolicy.RefusalDelay` |
| loosening option | One of the five options that loosen a secure default for tests: `--allow-anonymous`, `--allow-plaintext-auth`, `--auth <methods>`, `--self-signed` and `--throwaway-hostkey`. Each writes a startup warning, none is on by default, and there is no umbrella option; `surl --help testing` explains each (ADR-0032 sections 1 and 9, ADR-0034 decision 5, ADR-0051 decision 11). | `SurlCommandLine.AllowAnonymous`, `.AllowPlaintextAuthentication`, `.GivenAuthenticationMethods`, `.SelfSigned`, `.ThrowawayHostKey`; its help paragraph is `OptionHelp.Explanation` |
| startup warning | A `surl: warning: <option>: ...` line a loosening option writes on every start, after the command line is read and before any listener status line, in the order `--allow-anonymous`, `--allow-plaintext-auth`, `--auth`, `--self-signed` (only when the throwaway certificate is made), `--throwaway-hostkey` (only when the throwaway host key is made). Written to the log stream from the `info` log level up (ADR-0032 section 9, ADR-0033 section 7, ADR-0051 decision 11). | `AuthenticationComposition.WriteLooseningWarnings`; the `--self-signed` line by `CommandLineRunner`; the `--throwaway-hostkey` line by `SshHostKeyComposition.WriteStartLines` |
| throwaway certificate | The self-signed server certificate surl makes at start for a listen URL that is TLS from the first byte, or one that offers a TLS upgrade (`ftp`, `imap`, `pop3`, `smtp`), only when `--self-signed` is given and `--cert` is not; clients must skip verification (`curl -k`). Without either option a listen URL that is TLS from the first byte ends surl with 58 before any listener binds, and one that could upgrade offers no TLS upgrade; and `--self-signed` with `--cert` is refused (ADR-0032 section 10, superseding ADR-0010's default). | `ThrowawayServerCertificate` in `Surl.Networking.UnitLibrary`, made by `ServerTlsComposition` in `Surl.Composition`; its fingerprint `ServerTlsComposition.ThrowawayCertificateFingerprint` |
| checked login | A login whose credentials were checked against the accounts, accepted or refused, and the only kind the verbose log notes: `Login accepted: <method> <user>` or `Login refused: <method> <user>`, `<method>` the HTTP `Authorization` scheme, the SSH method name as on the wire (`password`, `keyboard-interactive`, `publickey`; ADR-0051 decision 7), the SASL mechanism's name in capitals or `APOP` (ADR-0049 section 7), or otherwise the listen URL's scheme (`ftp`, `ftps`, `mqtt`, `imap`, `pop3`, ...), `<user>` as sent (`bearer token` for Bearer, left out when unreadable). No credentials, a plain-text secret refused unchecked, no user name, a handshake's continuation step and `--allow-anonymous` are not checked logins (ADR-0032 section 8, ADR-0038). | `CheckedLogin` in `Surl.Protocol.Abstractions`, on `HttpAuthenticationVerdict.CheckedLogin`; a password login unchecked under `--allow-anonymous` is `PasswordLoginVerdict.AcceptedUnchecked` |
