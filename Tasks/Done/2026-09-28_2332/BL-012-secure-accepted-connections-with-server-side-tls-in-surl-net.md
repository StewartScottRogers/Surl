# BL-012 — Secure accepted connections with server-side TLS in Surl.Networking

## Goal

`Surl.Networking.UnitLibrary` implements the TLS contract from the TLS ADR (BL-002,
added to Abstractions by BL-006) over `SslStream`: server certificate and key, ALPN, and
optional client-certificate verification. It works both for a connection that is secured
from the first byte and for an upgrade in the middle of a connection.

## Context

- The TLS ADR recorded by BL-002 under `Documentation/Planning/Decisions/` is the
  specification: certificate sources and formats, the ALPN IDs offered, client
  certificates, platform differences. Its `README.md` index names it.
- The TCP connection adapter from BL-011 is what gets secured.
- Only `Surl.Networking` constructs `SslStream` (root `CLAUDE.md`).
- Fast tests may run `SslStream` over an in-memory duplex stream pair, with the client
  side being an `SslStream` in the test, because that opens no socket. Certificates are
  generated in the test with `CertificateRequest`, never read from a Windows certificate
  store or a committed file, so the tests pass on Windows, Linux and macOS. Where the ADR
  records a platform difference, pin each platform's behaviour in its own test with
  `[OSCondition]`.
- Upstream curl behaviour against this server (what `curl -k https://…` does) is proven
  end to end in a later conformance task, not here.

## Acceptance criteria

- [x] A TLS type in `Surl.Networking.UnitLibrary` implements the ADR's contract: secure
      an accepted connection with a given certificate, report the negotiated protocol
      and ALPN protocol, and support the upgrade the ADR defines.
- [x] Fast tests complete a handshake over in-memory streams with a certificate
      generated by `CertificateRequest`, and exchange application bytes both ways.
- [x] Fast tests prove ALPN selection for each protocol ID the ADR says `https` offers.
- [x] Fast tests prove client-certificate verification: a client certificate signed by
      the configured trust anchor is accepted, one that is not is rejected, and none is
      rejected when verification is required.
- [x] A failed handshake is reported as the ADR defines, with the `SurlExitCode` or
      exchange outcome it names, and a test pins it.
- [x] `dotnet build Surl.Networking.UnitLibrary -warnaserror` is clean, the fast tests
      are green, and `Measure-CodeQuality.ps1` reports no failing member in
      `Surl.Networking.UnitLibrary`.

## Notes

Wiring `https` into `surl` and proving it with pinned upstream curl belongs to follow-up
tasks, filed after this one lands.

What landed (ADR-0010 sections 1, 3 to 6):
- `StreamConnection.UpgradeToTlsAsync` runs `ServerTlsHandshake` (an `SslStream` over the
  transport, left open so the connection still owns it). Success swaps reads and writes to
  the `SslStream` and sets `TlsSession` (version, cipher suite, ALPN, SNI, a copy of the
  verified client certificate). `AuthenticationException` or `IOException` becomes
  `TlsHandshakeException`; cancellation stays `OperationCanceledException`; an abort mid
  handshake is the usual aborted `IOException`. After any unfinished handshake the connection
  is unusable and disposing it writes nothing (no FIN), per ADR-0006 section 4.
- `ServerTlsSettings` (public), `ThrowawayServerCertificate` (public),
  `ClientCertificateVerifier`, `ServerCertificateImport`, `TlsApplicationProtocols`.
  `TcpConnectionListener.StartAsync(listenUrl, tlsSettings, token)` and
  `new SocketListenerFactory(tlsSettings)` carry the settings to every accepted connection.

Decisions (defaults taken under the delegation; all inside ADR-0010, so no new ADR):
- A connection whose listener has no `ServerTlsSettings` refuses `UpgradeToTlsAsync` with
  `InvalidOperationException`: the composition root, not the connection, decides whether
  TLS is configured (it builds the throwaway certificate when ADR-0010 says to).
- `CompleteWritesAsync` on a secured connection sends TLS close_notify before FIN, the
  orderly TLS close; plaintext connections are unchanged.
- Versions are left to the operating system (`EnabledSslProtocols` unset) and renegotiation
  is untouched: BL-048 owns the version range and renegotiation refusal.
- The certificate handed to `ServerTlsSettings` needs an exportable key, because it is
  re-imported through PKCS#12 (ADR-0010 section 6). Measured on Windows: a certificate from a
  default PKCS#12 import cannot be exported ("Key not valid for use in specified state").
  `CertificateRequest` and PEM imports are exportable; BL-067's loader must import PKCS#12
  with `Exportable`.
- No CA list is sent in the certificate request (no `CertificateTrust` set), as ADR-0010
  section 5 says.
- ALPN with no protocol in common is not tested: unreachable from the pinned build, and the
  ADR says it is pinned per platform only if tested.

Learned:
- `SslStream` sends its handshake-failure alert with a synchronous `Stream.Write`, so the
  test pipe implements it.
- An `await` inside `finally` leaves compiler-generated branches coverage cannot reach; the
  failed handshake disposes the `SslStream` synchronously instead.

Follow-up filed: BL-067 (read the `--cert`, `--key` and `--cacert` files into
`ServerTlsSettings`, the part of ADR-0010's consequences the acceptance criteria here did
not cover). BL-048 (versions, renegotiation), BL-065 (engine performs the implicit
handshake and notes it) and BL-038 (`https` in `surl` against pinned upstream curl) already
existed.

`dotnet format --verify-no-changes` reports only `Surl.Cli.UnitLibrary\SchemeDefaultPorts.cs`,
outside this task's `touches`; it was already failing before this change.
